# 05 — Database Schema, Migrations, and Data-Access Layer

## 1. Database Architecture & Connection Model

- **Engine**: Supabase PostgreSQL accessed directly over TLS 1.2+ via the Node.js `pg` driver (`^8.12.0`).
- **Primary Client ([`lib/postgres.js`](file:///d:/ihuriroryamata.com/lib/postgres.js))**:
  - Creates a singleton `pg.Pool` (`max: 10`, `idleTimeoutMillis: 30000`, `connectionTimeoutMillis: 10000`) using `process.env.DATABASE_URL` and the pinned Supabase Root 2021 CA certificate ([`lib/supabase-root-ca-2021.js`](file:///d:/ihuriroryamata.com/lib/supabase-root-ca-2021.js)) with `ssl: { rejectUnauthorized: true, ca: supabaseRootCa }`.
- **Row-Level Security (RLS) Policy**:
  - **PostgreSQL RLS is intentionally disabled across all 33 tables.** As documented in [`supabase/migrations/README.md:19-22`](file:///d:/ihuriroryamata.com/supabase/migrations/README.md#L19-L22) and enforced by [`tests/migration-grants.test.js:110-122`](file:///d:/ihuriroryamata.com/tests/migration-grants.test.js#L110-L122), all tenant isolation is enforced in the application repository layer via parameterized `owner_user_id` filters.
- **PostgreSQL Role Grants Convention (`001`–`018` vs `019`–`022`)**:
  - Migrations `001`–`018` (30 tables) contain no explicit `GRANT` statements (grandfathered in `tests/migration-grants.test.js:12-31`).
  - Starting with `019_import_batches.sql` (ahead of the October 30, 2026 Supabase Data API default-grant change), every newly created table explicitly declares least-privilege grants (`authenticated` + `service_role` on `import_batches` and `farmer_field_configurations`; `service_role` only on `platform_job_runs`; zero grants to `anon`).
